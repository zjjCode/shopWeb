### <a id="log-011"></a>[2026-09-06 · 阶段 1] T020 第 1 批（缓存组件 + 分类树）：CacheService 降级定位、孤儿节点处理裁定、T020 拆分执行

- **背景**：T020「分类/商品/SKU 前台查询 + Redis 缓存」是「登录 → 商品浏览 → 加购 → 下单 → 支付」最小闭环的第二环。首次派发（8 个文件）**跑到 2 分 32 秒即被 API 429 限流打断，零产出**；环境仍然**无 MySQL、无 Redis 实例**，不能真跑接口，验证只能靠 `tsc` + 单测（mock）。
- **决策**：
  1. **T020 拆成两批执行**：本批只做「缓存组件 + 分类树」4 个文件（CacheService / CategoryService / CategoryController / app.ts 挂载 + `routes/api/catalog.routes.ts`），第 2 批再做商品/SKU/库存。**不提前实现商品相关文件**。理由：单批文件越多，被限流打断时已落盘但未自测的代码越多（T010 那批曾因此留下 22 个编译错误），缩小批次可保证「写完即自测完」。
  2. **CacheService 定位：Redis 只做性能与并发辅助，绝不做权威源**（直接落实 `docs/02-architecture.md:61`「资金/库存/订单状态的权威源永远是 MySQL」）。因此**任何 Redis 故障都不得阻断业务**：
     - `get`：Redis 不可用 / 命令抛错 / 内容非 JSON / 未命中 → 一律返回 `null`，调用方走查库路径；
     - `set` / `del` / `delByPattern`：静默失败 + `logWarn`，返回 false / 0，绝不向上抛错；
     - `getOrSet`（缓存旁路）：Redis 挂了**依然执行 loader 回源**，只是不回填 —— 没有缓存不等于查不到数据。
     与 `src/core/redis.ts`、`AuthService` 登录失败锁定的降级哲学一致：**保护措施不应比它要防护的故障更致命**。
  3. **Key 生成收敛到一处**：`CacheService.buildKey(namespace, ...parts)` 生成 `「前缀:命名空间:参数」`，前缀取 `config.redis.keyPrefix`（默认 `'shop'`，即 `REDIS_KEY.PREFIX`），命名空间取 `REDIS_KEY.*` 常量。**业务代码禁止自行拼接 `shop:` 前缀**（与既有 `rateLimit.ts` / `AuthService` 的 `config.redis.keyPrefix` 写法保持一致）。所有缓存键显式带 TTL（§5.9）。
  4. **BigInt 序列化坑**：金额是 `BIGINT`，Prisma 返回 JS `bigint`，`JSON.stringify` 遇到 bigint 直接抛 `TypeError`。CacheService 统一复用 `@/core/response` 的 `safeStringify`（内置 bigint → number，超安全范围降级为字符串）与 `parseJson`（解析失败返回 null），响应层与缓存层口径一致。序列化单独 `try`：该失败属于「数据不可序列化」而非「Redis 故障」，日志要能区分。
  5. **`delByPattern` 用 SCAN 不用 KEYS**：KEYS 会一次性遍历整个键空间并阻塞单线程 Redis，键多时等同于一次线上故障。
- **实现要点**：
  1. **分类树：一次性查库 + 内存两趟组装，禁止 N+1 递归**。第一趟按 `sort` 升序、`id` 升序稳序并建 `Map<id, node>`；第二趟按 `parentId` 挂父子（O(1) 命中）。无递归，因此即便数据成环（a→b→a）也不会死循环，环上节点只是进不了根节点数组。
  2. **孤儿节点裁定：跳过（连同其子树一起不展示），而不是降级为一级节点**。理由：① 与电商惯例一致 —— 父级禁用/删除语义上就是整棵子树下架，降级为一级会让已下架品类的商品重新出现在首页导航，属脏数据外泄；② 父级缺失意味 `path`（形如 `/1/2/3/`）与 `level` 的对应关系断裂，降级会输出「level=2 却挂在根下」的畸形节点，前端面包屑与层级筛选会错；③ 孤儿 ID 由 `CategoryService.queryTree()` 打 `category.orphan_nodes` warn 日志（最多记 20 个），便于运营修数据 —— 若静默降级，这类数据质量问题将永远无人发现。**注意**：`orphanIds` 只记录**直接**父级缺失的节点，因祖先缺失而被连带隐藏的后代不在其中（其父级在结果集里，只是整棵子树没挂到根上），这正是期望语义。
  3. 只查 `status = ENABLED` 且 `deletedAt = null`；排序下推给 DB（`idx_status_level_sort` / `idx_parent_sort`），内存侧再兜一次稳序保证输出可缓存、前端可 diff。缓存 TTL 10 分钟（`docs/02-architecture.md:1239`：分类树 10min / 商品 5min / 价格 60s）。
  4. 响应体统一包一层 `{ list: tree }` 而非直接返回数组：与 `sendPaged` 的 `{ list, total }` 信封风格一致，日后追加 `updatedAt` 等元信息不会构成破坏性变更。ID 转字符串输出（沿用 `UserPayload` 先例），从源头规避 bigint 序列化问题。
- **产出**：
  - 新增：`src/services/CacheService.ts`（229 行）、`src/services/CategoryService.ts`（231 行）、`src/controllers/CategoryController.ts`（41 行）、`src/routes/api/catalog.routes.ts`（53 行）、`src/tests/unit/categoryTree.spec.ts`（360 行，14 个用例）
  - 修改：`src/app.ts`（挂载 `app.use('/api', catalogRouter)`）
  - 文档：`docs/07-开发流程记录.md`（本条）
- **影响/注意**：
  1. **⚠️ 未经真实库/Redis 验证**：分类树查询、缓存回填与过期**全部未在真实 MySQL / Redis 上跑过**。待实例就绪后必须补跑 `prisma migrate` + seed，再验证 `GET /api/categories` 的层级、排序与缓存命中（第二次请求应不再查库）。

### <a id="log-009"></a>[2026-09-05 · 阶段 1] T010 认证模块（注册/登录/刷新/登出，双 scope）：注册同事务开户裁定、双锁定机制差异、refresh 轮换与整族吊销

- **背景**：T010 是「用户注册登录 → 商品浏览 → 下单」最小闭环的第一环，需做到可被后续模块直接依赖的完成度。环境**无 MySQL、无 Redis 实例**，不能真跑接口，验证只能靠 `tsc` + 单元测试（mock）。
- **决策**：
  1. **注册同事务开户（文档矛盾裁定）**：`docs/03-database.md:2275` 明确要求「**用户注册时同事务创建 `USER_BALANCE` 账户**（事务 H）」，`User` 模型注释（03-database.md:473，schema 中亦有对应注释）重复了这条；但 `docs/04-flows.md` 的 F1 注册时序图**漏画了这一步**（v2 变更未同步）。**裁定：按 03-database.md 执行，注册必须同事务开户**。理由：漏了会导致后续余额/充值/支付全线无账户可用，且历史用户要补开户。已在 `AuthService.register()` 内用 `withTransaction(label:'auth.register')` 包裹 `users` INSERT + `fund_accounts` INSERT，并在代码注释中记录该矛盾。
  2. **C 端与后台失败锁定机制刻意不同**：
     - **C 端（`users`）→ Redis**：`users` 表**没有** `loginFailCount` / `lockedUntil` 字段，故失败计数与锁定只能用 Redis（`shop:rl:login:fail:{phone}` 计数、`...:lock:{phone}` 锁定，5 次锁 15 分钟）。Redis 不可用时**降级放行**（与 `rateLimit.ts` 的失败放行策略一致：保护措施不应比它要防护的故障更致命）。
     - **后台（`admin_users`）→ DB 字段**：`AdminUser` 模型本身就有 `loginFailCount` / `lockedUntil` 两个字段，因此后台直接用这两个 DB 字段实现「5 次锁定 15 分钟」，**不套用 C 端 Redis 方案**。锁定时长与 C 端一致（15 分钟）。
     - 差异原因：**载体跟着模型走**——表里有的字段就用表，没有才退到 Redis。这样后台锁定是持久化且事务安全的，不会因 Redis 重启而失效（后台账号是高价值攻击目标，锁定状态必须持久）。

### <a id="log-001"></a>[2026-09-02 · 设计基线] v2 设计定稿（四项客户变更 + 取消混合支付）

- **背景**：客户在 v1 设计确认后提出四项变更：① 做优惠券/促销 ② 做动态角色管理台 ③ 支付接银行卡 ④ 用户余额账户 + 充值 + 消费；随后追加更正「去掉混合付款，单独支付就行」。
- **决策**（均为已确认的技术决策，代码实现必须遵循）：
  - **单一支付**：`pay_method` 单值，一笔订单只走一条路径；退款按 `pay_method` 单一路由（余额→退回余额，渠道→原路退回）。
  - **记账模型方案 A+**：单式流水 + `counterparty_account_id` + `tx_group_no` + `is_liability`。用 3 个字段拿到复式记账 90% 的语义，避免全局负债池热点行与全表重写。余额本质是**平台对用户的负债**，消费时写「负债结转对」确认收入。

  - **支付回调统一异步**：mock/支付宝/微信/银行卡全部走 BullMQ，避免两条代码路径维护两套幂等与回滚逻辑。
  - **银行卡走聚合服务商**（拉卡拉/收钱吧），非直连银联：进件周期 4~8 周超工期，且托管收银台可规避 PCI-DSS 合规义务（卡号不落地）。
  - **部分退款提 P0**：取消混合支付后无跨来源拆分，成本下降；「一单多件退一件」是高频售后。
- **产出**：`docs/02-architecture.md`(v2)、`docs/03-database.md`(v2)、`docs/05-PRD-变更.md`(v1.1)
