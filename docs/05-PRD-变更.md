## 2. 模块一：优惠券 / 促销（CPN）

### 2.1 用户故事

1. 作为**买家**，我希望在领券中心看到可领取的券并一键领取，以便下单时直接省钱。
2. 作为**买家**，我希望结算页自动列出「本单可用券」并标出最省的一张，以便不用自己逐张试算。
3. 作为**买家**，我希望下单时系统自动帮我选中最优惠券、我也可以手动切换，以便把选择权留给我。
4. 作为**买家**，我希望整单退款后我的券能退回「未使用」，以便不会因一次退款白白损失优惠。
5. 作为**买家**，我希望商品详情页能看到该商品可用的券与促销活动，以便下单前就知道能省多少。
6. 作为**运营**，我希望创建满减/折扣/无门槛券，配置门槛、限领、有效期与适用范围，以便做精细化营销。
7. 作为**运营**，我希望配置满减 / 满折 / 限时折扣活动并指定参与商品，以便批量拉动销量。
8. 作为**运营**，我希望看到券的领取量、使用量、核销率与带动 GMV，以便评估活动效果。

### 2.3 业务规则

#### 2.3.1 券的面额与折扣表达（沿用 §6.1 金额公约）

| 券类型 | 使用门槛 | 优惠表达 | 封顶 | 举例 |
| --- | --- | --- | --- | --- |
| 满减券 `FULL_REDUCE` | `threshold_amount`（分），> 0 | `discount_amount`（分） | — | 满 19900 减 3000 |
| 折扣券 `DISCOUNT` | `threshold_amount`（分） | `discount_rate`（**万分比整数**） | `max_discount`（分，**必填**） | 满 10000 打 85 折（`8500`），最高减 5000 |
| 无门槛券 `NO_THRESHOLD` | 固定 `0` | `discount_amount`（分） | — | 无门槛减 500 |

**计算规则**：
- 满减券：`discount = min(discount_amount, 促销后商品金额合计)`
- 折扣券：`discount = min(促销后商品金额合计 * (10000 - discount_rate) / 10000, max_discount)`，**向下取整到分**
- 门槛判定基于**促销后**的商品金额（即先算促销再判券），不含运费。

#### 2.3.2 券生命周期状态机

```

         │
         ▼
   ┌───────────┐  到达开始时间    ┌───────────┐  用户领取(校验：余量/限领/活动期)
   │  未开始    │ ──────────────► │  可领取    │ ─────────────────────┐
   │ NOT_START │                  │ CLAIMABLE │                      │
   └───────────┘                  └───────────┘                      │
                                        │                            ▼
                                        │                    ┌───────────────┐
                                        │        ┌──────────►│ 已领取·未使用   │
                                        │        │  解冻     │ UNUSED        │
                                        │        │           └───────┬───────┘

                                        │        │                   ▼
                                        │        │           ┌───────────────┐
                                        │        └───────────│ 已占用·锁定    │
                                        │  支付失败/取消/超时 │ LOCKED        │

**「已占用/锁定」状态：推荐单独设立。** 理由：若支付过程中券仍为「未使用」，用户可在另一设备/另一订单中重复使用同一张券，造成**一券多用**。锁定后：支付成功 → 已使用；支付失败 / 用户取消 / 超时关单 → 解冻回「未使用」。

#### 2.3.3 限领与限用规则

| 规则项 | 推荐值 | 理由 |
| --- | --- | --- |
| 每人限领 | **1 张**（模板可配 1~10） | 默认 1 张可最大化券的覆盖面；大促场景由运营按需放开 |
| 每单限用 | **1 张**（`order.maxCouponPerOrder` 可配） | 多券叠加会让优惠计算与退款分摊复杂度指数上升，收益不成正比 |
| 券与券 | **互斥**（每单 1 张，天然互斥） | 同上 |
| 券与促销 | **默认可叠加**；券模板可勾选「不与促销同享」 | 叠加能放大营销效果；但需给运营「关掉」的开关以控成本 |
| 券与运费 | **不抵扣运费**（可配，默认关） | 运费是履约成本，不应被营销成本稀释 |
| 券与余额 | **可叠加**（先算券，券后 `pay_amount` 即余额支付金额） | 见第 5 章计算顺序；选余额支付时支付金额 = 券后全额（单一支付，不拆分） |
| 排除范围 | 券的适用范围内可指定 SKU 黑名单 | 特价品、清仓品不应再享券 |

#### 2.3.4 有效期

| 方式 | 字段 | 适用 | 推荐 |
| --- | --- | --- | --- |
| 固定时间段 | `valid_start` + `valid_end` | 大促券、节日券 | **默认推荐**：运营可精确控制活动节奏，到期集中，便于短信召回 |
| 领取后 N 天 | `valid_days`，领取时计算 `expire_at` | 新客券、常驻券 | 次选 |

过期处理：定时任务（建议每日 02:00 + 每小时增量扫描）批量将 `UNUSED` 且 `expire_at < now` 的券置为 `EXPIRED`。

#### 2.3.5 优惠分摊（重点）

**为什么必须分摊**：部分退款必须按行退款，行退款额 = 行实付 = `行金额 - 该行分摊的优惠`。**若订单级优惠不分摊到行，就无法确定单件商品退多少钱**，也无法满足「累计退款 ≤ 订单实付」的校验，最终必然出现多退/少退的资损。

**分摊算法（推荐）**：
1. 权重：`weight_i = 该行促销后商品金额`（`row_goods_amount - row_promo_discount`）
2. 逐行：`allocated_i = floor(total_discount * weight_i / total_weight)`
3. 尾差：`remainder = total_discount - Σ allocated_i`，将 `remainder` 加到 **权重最大**的行（并列时取行号最小者）
4. 截断保护：若 `allocated_i > weight_i`，则 `allocated_i = weight_i`（行实付最小为 0 分），截断出的金额按步骤 3 规则补到其它行
5. 分摊结果**固化到订单行快照**（`allocated_discount`），后续退款直接读取，不再重算

**分摊范围**：仅订单级优惠（订单级满减、优惠券）需要分摊；行级促销（限时折扣、满折）天然归属该行，无需分摊。
**运费不参与分摊**，运费单独处理（整单退才退运费）。

**示例**：商品 A ¥120.00（12000 分）、商品 B ¥80.00（8000 分），满 199 减 30（3000 分）。
→ A 分摊 `floor(3000*12000/20000)=1800` 分，B 分摊 `floor(3000*8000/20000)=1200` 分，合计 3000，尾差 0。
→ A 行实付 10200 分，B 行实付 6800 分。退 B 一件 → 退 6800 分。

#### 2.3.6 退款时的优惠处理（重点）

| 退款场景 | 券是否返还 | 已分摊优惠处理 | 退款额计算 |
| --- | --- | --- | --- |
| **整单退款**（未发货/已发货/售后，全退） | ✅ **返还**：券回到「已领取未使用」；若已过期则返还后自动置为「已过期」 | 全额退还已分摊优惠 | `退款额 = 订单实付（= pay_amount）`，按订单的**唯一支付来源**退回：余额订单退余额、渠道订单原路退 |
| **部分退款**（退其中几行） | ❌ **不返还** | 按行退还该行已分摊的优惠 | `退款额 = Σ(行金额 - 行促销优惠 - 行分摊优惠)` |
| **部分退款**（退单行中的部分数量） | ❌ **不返还** | 按 `退款数量 / 行数量` 比例退还该行分摊优惠 | 按比例计算，向下取整 |
| 退运费 | — | — | 仅整单退时退还运费；部分退默认不退（可配） |

> **v1.1 说明**：取消混合支付后，退款不再需要在余额与渠道之间拆分（无需 PRO_RATA 等分配规则），一笔退款**只有一个去向**。上表「券是否返还」「行级优惠退还」「运费」三条规则**不受影响，继续生效**。

**推荐理由**：
- **整单退返还券**：交易整体取消，相当于"这笔买卖没发生"，券理应回到未使用状态，符合用户直觉，也是主流电商做法。
- **部分退不返还券**：交易部分成立，券的营销目的（拉动首单/提升客单）已达成；若允许"买 3 件用券后退 2 件"，用户可**套利**（用大额券的门槛凑单后再退，白拿优惠）。这是明确的资损风险，必须堵住。

**补充**：整单退款返还券时，若券已过期，**不延长有效期**（避免无限期延期），返还后由定时任务或即时判定置为「已过期」，并在退款结果页告知用户"券已过期，未能返还"。

#### 2.3.7 促销活动

| 活动类型 | 作用层级 | 规则 | 一期 |
| --- | --- | --- | --- |
| 满减 `FULL_REDUCE` | **订单级**（按参与商品金额合计判定门槛） | 满 N 分减 M 分；可设阶梯（满 100 减 10 / 满 200 减 25，取最高档） | ✅ P0 |
| 满折 `FULL_DISCOUNT` | **行级**（按参与商品逐行打折） | 满 N 件或满 N 分，参与商品打 X 折（`discount_rate` 万分比） | ✅ P0 |
| 限时折扣 `FLASH_SALE` | **行级**（直接改行价） | 指定商品在时间段内按折扣价/固定价销售 | ✅ P0 |
| 第 N 件半价、秒杀、拼团 | — | — | ❌ P2 / 二期 |

**活动与券的优先级**：**先算活动，再算券**（行级活动 → 订单级活动 → 券）。理由：活动是平台定价行为（改的是"售价"），券是用户持有的资产（减的是"应付"）；先改价再核券，券的门槛判定才符合用户在商品页看到的促销价。

**活动互斥**：同一商品同时命中多个限时折扣 → 取**优惠力度最大**的一个，不叠加。同一订单命中多个满减活动 → 取**优惠力度最大**的一个（阶梯除外，阶梯内取最高档）。

#### 2.3.8 新金额恒等式（替换 01-PRD §6.1）

```
goods_amount            商品原价合计（Σ 行单价 × 数量）
  - row_promo_discount    行级促销优惠（限时折扣 / 满折）
  - order_promo_discount  订单级促销优惠（满减，已分摊到行）
  - coupon_discount       优惠券优惠（已分摊到行）
  + freight               运费
  ────────────────────────────────────────────
  = pay_amount            应付金额（= 订单唯一支付单的金额）
```

> **v1.1 简化**：取消混合支付后**不再有 `balance_paid` / `channel_paid` 两个拆分字段**。
> `pay_amount` 是订单的唯一支付金额，**支付方式只决定这笔钱从哪出，不拆分金额**：
> 选余额 → 支付单 `channel=BALANCE`，金额 = `pay_amount`；选支付宝/微信/银行卡 → 支付单 `channel=ALIPAY/WECHAT/BANKCARD`，金额 = `pay_amount`。
> 订单表只需记录 `pay_method`（支付方式）+ `pay_amount`，不需要记录拆分金额。

**校验约束（任一不满足则拒绝下单并告警）**：

| 约束 | 表达式 |
| --- | --- |
| ① 恒等式 | `goods_amount - row_promo_discount - order_promo_discount - coupon_discount + freight == pay_amount` |
| ② 单一支付 | `支付单金额 == pay_amount`，且一笔订单**有且仅有** 1 个支付单（`channel` ∈ `BALANCE` / `ALIPAY` / `WECHAT` / `BANKCARD` / `MOCK`） |
| ③ 分摊守恒 | `Σ 行分摊优惠 == order_promo_discount + coupon_discount` |
| ④ 行实付守恒 | `Σ 行实付 + freight == pay_amount`，其中 `行实付 = 行金额 - 行促销优惠 - 行分摊优惠` |
| ⑤ 非负 | 所有扣减项 ≥ 0；`row_promo_discount + 行分摊优惠 ≤ 行金额`；`pay_amount ≥ 0` |
| ⑥ 余额充足（选余额时） | `balance.available >= pay_amount`，否则拒绝（不允许部分抵扣，不允许透支） |
| ⑦ 整数 | 全链路「分」整数运算，误差恒为 0（禁止浮点） |

## 3. 模块二：动态角色管理台（RBAC）

> **变更说明**：01-PRD §2 的 4 个静态枚举角色（guest / user / admin / super_admin）**改为动态可配置角色**。C 端角色（guest / user）保持静态（不涉及后台权限），后台角色全部动态化。`ADMIN-08` 由 P1 上调为 P0 并细化为下列 RBAC-* 条目。

### 3.1 用户故事

1. 作为**超级管理员**，我希望创建自定义角色并勾选权限点，以便按岗位（客服/运营/财务）分配最小权限。
2. 作为**超级管理员**，我希望给一个管理员分配多个角色，权限取并集，以便一人多岗不必建"组合角色"。
3. 作为**超级管理员**，我希望删除已关联用户的角色时被系统阻止或引导转移，以便不产生"无角色的管理员"。
4. 作为**超级管理员**，我希望修改权限后即时生效，以便出现风险时能立刻收回权限。
5. 作为**运营**，我希望只能看到和操作自己创建的商品（数据权限），以便多人协作时互不干扰、互不误改。
6. 作为**超级管理员**，我希望查看"谁在什么时候把谁的权限改成了什么"的审计日志，以便权限变更可追责。
7. 作为**超级管理员**，我希望后台菜单按当前权限动态渲染，以便不同角色看到不同后台，降低误操作。

### 3.2 需求池（RBAC：15 条 = P0 12 / P1 2 / P2 1）

| 编号 | 模块 | 需求描述 | 优先级 | 验收标准 |
| --- | --- | --- | --- | --- |
| RBAC-01 | 角色权限 | 权限点定义：`资源:操作` 粒度（如 `product:create`、`order:refund:audit`），集中声明并启动时注册 | P0 | 权限点清单可枚举、可导出；新增权限点无需改校验逻辑 |
| RBAC-02 | 角色权限 | 角色 CRUD：名称、编码（唯一）、描述、状态（启用/停用）、权限点集合、数据范围 | P0 | 角色编码唯一；停用角色的关联用户立即失去该角色权限 |
| RBAC-03 | 角色权限 | 内置超级管理员角色：不可删除、不可编辑权限；系统至少保留 1 个启用且绑定该角色的账号 | P0 | 删除/改权操作被拒绝；最后一个超管账号不可禁用或解绑 |
| RBAC-04 | 角色权限 | 角色删除校验：存在关联用户时禁止删除，提示"请先转移用户"，并提供批量转移 | P0 | 有用户关联时删除失败且有明确提示 |

| RBAC-06 | 角色权限 | 多角色权限合并：权限点取**并集**；数据范围取**最宽** | P0 | 任一角色有权限即放行；任一角色为「全部」则数据范围为全部 |
| RBAC-07 | 角色权限 | 权限校验中间件：解析用户 → 角色 → 权限集合 → 校验 `资源:操作`；无权限返回 403 | P0 | 未登录 401；无权限 403；越权访问数据 403 |
| RBAC-08 | 角色权限 | 权限缓存与生效时机：服务端缓存（默认 60s）+ 变更时主动失效；敏感权限即时生效 | P0 | 普通权限 ≤ 60s 生效；敏感权限下次请求即生效 |

| RBAC-14 | 角色权限 | 后台登录失败锁定：连续 5 次失败锁定 30 分钟（可配） | P1 | 触发锁定返回明确提示；锁定期间正确密码也拒绝 |
| RBAC-15 | 角色权限 | 临时权限：角色/权限带有效期，到期自动回收 | P2 | 到期后权限自动失效 |

### 3.3 业务规则

#### 3.3.1 权限点粒度

- **格式**：`资源:操作`，两段式为主，特殊场景三段式（如 `order:refund:audit`）。
- **操作枚举**：`list`（查看列表）、`detail`（查看详情）、`create`、`update`、`delete`、`export`、`audit`（审核）、`adjust`（调账）、`publish`（发布）。
- **资源清单（一期）**：`product`、`category`、`sku`、`stock`、`order`、`refund`、`coupon`、`promo`、`user`、`balance`、`fund`、`rbac:role`、`rbac:admin`、`pay:channel`、`log`。
- **是否做数据权限**：**推荐做**（一期两档）。理由：多人运营后台没有数据隔离，误改他人商品是高频事故；注入 `creator_id` 过滤的实现成本低、收益高。`DEPT`（本部门）档位组织树依赖较重，列 P2。

#### 3.3.2 角色与管理员

| 规则项 | 规定 |
| --- | --- |
| 一个管理员多角色 | ✅ 支持（多对多） |
| 多角色权限合并 | 权限点取**并集**（任一角色有即放行） |
| 多角色数据范围合并 | 取**最宽**（任一角色为 `ALL` 则整体 `ALL`） |
| 内置角色 | `SUPER_ADMIN`：不可删除、不可编辑权限、不在角色列表中显示删除/编辑按钮；系统强制保留 ≥ 1 个启用账号 |
| 内置角色（次） | `ADMIN`（普通管理员）：可编辑权限，但**不可删除**（P0 保护），避免误删基础角色 |
| 角色删除 | 有关联用户 → **禁止删除**，提示"请先转移用户"；提供「转移用户到指定角色后删除」批量操作（P1） |
| 角色停用 | 允许停用，停用它所属权限立即对该角色下所有用户失效（即时，非 60s 缓存） |
| 无角色管理员 | 允许存在（登录后无任何后台权限，仅可见空菜单）；但列表需高亮提示 |

#### 3.3.3 生效时机

| 权限类别 | 生效方式 | 举例 |
| --- | --- | --- |
| 普通权限 | 服务端权限缓存 **60s**（可配）+ 变更时主动失效；用户侧最迟 60s 生效 | `product:update`、`order:list` |
| **敏感权限** | **即时生效**（绕过缓存，每次实时判定） | `order:refund:audit`、`balance:adjust`、`rbac:role:*`、`rbac:admin:*` |
| 角色停用 | **即时生效** | — |
| 前端菜单 | 下次拉取权限/刷新页面后更新；被移除权限时已在页面上操作 → 服务端 403 拦截 | — |

**理由**：60s 缓存避免每次请求查库；敏感权限涉及资金，1 分钟的窗口期都可能造成资损，必须实时。

#### 3.3.4 审计

**权限变更本身必须记审计日志**（扩展 01-PRD `ADMIN-06`）。记录内容：操作人 ID、操作时间、IP、操作类型（创建角色/修改权限/分配角色/停用角色/删除角色）、目标对象、**权限前后差异 JSON**、备注。
权限变更审计日志**归入操作日志，不可删改**，且需支持按操作人、按目标角色两个维度查询。

| 方案 | 资质门槛 | 接入周期 | 费率 | 维护成本 | 评价 |
| --- | --- | --- | --- | --- | --- |
| **A. 聚合支付服务商**（Ping++ / 收钱吧 / 汇付 / 连连 / 富友） | **低**：企业营业执照 + 对公账户 + 网站备案，1 份协议 | **1~2 周** | 网关约 0.6%~1.0% | 低：一个 SDK 覆盖主流银行 | ✅ **推荐** |
| B. 直连银联（全渠道/云闪付） | **高**：需银联入网、专线或 VPN、PCI-DSS 相关合规、技术认证 | **2~3 个月起** | 约 0.3%~0.55%（更低） | 高：报文规范、证书、对账均需自研 | ❌ 一期不建议 |
| C. 支付宝/微信内的「绑卡快捷」 | 复用已有支付宝/微信商户号 | 已含在 A 渠道内 | 同支付宝/微信费率 | 低 | ⚠️ **不算独立银行卡渠道** |

**推荐 A（聚合支付服务商）的理由**：
1. **资质与周期**：直连银联需要入网审批、专线/VPN、技术认证与合规评审，周期以"月"为单位；聚合商一份协议 + 一个 SDK 即可覆盖主流银行，1~2 周可联调完成，与一阶段交付节奏匹配。
2. **综合成本**：聚合商费率虽高约 0.3~0.5 个百分点，但省掉的是 2~3 个月的人力与机会成本；一期交易量下，费差远小于人力成本。
3. **可替换性（关键）**：`BankCardAdapter` 依赖的是**我们自己的统一接口**，不是聚合商的 SDK 语义。未来换聚合商或升级为直连银联，只需替换 adapter 实现 + 改配置，**业务代码零改动** —— 这正是适配器模式的价值所在。
4. **关于方案 C**：支付宝/微信内的"绑卡快捷"本质是走支付宝/微信通道，只是资金来源为银行卡。它不能替代一个独立的「银行卡」渠道（用户未装支付宝/微信时无法使用），但可作为一种便利选项保留。**建议在收银台上把「银行卡」作为独立入口，不要与支付宝/微信混为一谈**。

> ⚠️ **需客户确认**：是否已有营业执照/对公账户/网站备案？是否已签约或有偏好的聚合服务商？这三个要素决定银行卡渠道能否在一期落地（见 Q-B3）。

#### 4.3.4 退款规则

| 规则项 | 规定 |
| --- | --- |
| **是否原路退回** | **是，强制默认**。一笔订单只有一个支付来源，退款去向唯一、无需拆分：<br>**余额支付的订单 → 全额退回用户余额账户**；**渠道支付的订单 → 原路退回原渠道** |
| 余额订单退款 | 写 `BALANCE_REFUND`（IN）流水 + 增加用户余额，**本地事务，无外部调用，即时到账**；不调用渠道 `refund` |
| 渠道订单退款 | 调用该渠道 `refund` 原路退回；**不允许改退余额**（一期不做提现，退余额等于变相提现，见 Q-B16） |
| 多次部分退款 | ✅ 支持；同一支付单可多次退款，**累计 ≤ 该支付单实付** |
| 每次退款 | 生成独立退款单号（`R` 前缀）；余额订单独立记账，渠道订单独立调用 `refund` |
| 渠道退款失败 | 自动重试 3 次（间隔递增）；仍失败 → 退款单置「退款失败」，保留原因，支持人工重试 |
| 原路失败降级 | 支持审批后改退用户余额（`PAYC-08` P1），需 super_admin 审批 + 审计日志 + 告知用户 |
| 退款有效期 | 微信/支付宝一般支持 1 年内退款；超期需人工处理（线下打款或退余额）并提示 |
| 分账退回 | 一期不做分账（`PAYC-16` P2），故不存在分账退回问题 |
| 退款与手续费 | 渠道退款时一般不退还已扣手续费；需在退款单记录"实退金额"与"手续费损失"，便于财务核算 |

#### 4.3.5 模拟支付的保留（**推荐保留**）

| 用途 | 说明 |
| --- | --- |
| ① 沙箱环境 | dev/test 环境默认渠道，无需真实商户号即可跑通全链路（含自动化测试用例） |
| ② 生产降级 | 渠道大面积故障时，人工开启 mock 作为应急（**默认关闭**，开启需 super_admin + 二次确认 + 审计日志 + 事后必须补对账） |
| ③ 演示环境 | 给客户/投资人演示时避免真实扣款 |

**注意**：生产环境开启 mock 会产生"有订单无真实资金"的账，必须在资金流水上打标 `is_mock=true`，对账时单独剔除。

## 5. 模块四：用户余额账户 + 充值 + 消费（BAL）

> **这是四项变更中影响面最大的一项**：资金模型由「单账户（平台收入）」升级为「**双账户（平台收入 + 用户余额负债）**」，详见第 6 章影响清单。

### 5.1 用户故事

1. 作为**买家**，希望用支付宝/微信/银行卡给平台余额账户充值，以便后续下单不必每次拉起支付。
2. 作为**买家**，希望下单时在余额和三个支付渠道之间**任选其一**付款，以便按自己的资金情况决定（**不做组合支付**）。
3. 作为**买家**，希望余额不足时能看到明确提示并一键去充值，以便不用来回试错。
4. 作为**买家**，希望查看余额明细（充值/消费/退款/赠送/调账），以便清楚每一分钱的来龙去脉。
5. 作为**买家**，希望退款时钱能退回余额账户并可查，以便资金去向明确、可追溯。
6. 作为**管理员**，希望在后台查询某用户的余额与变动明细、并在投诉场景下手工调账，以便快速处理客诉。
7. 作为**财务**，希望每日校验「用户余额合计 == 余额流水净额合计」，以便余额体系账实相符。

### 5.2 需求池（BAL：19 条 = P0 16 / P1 2 / P2 1）

| --- | --- | --- | --- | --- |

### 5.3 业务规则

#### 5.3.1 充值

| 规则项 | 推荐值 | 理由 |
| --- | --- | --- |
| 充值渠道 | **复用 PAYC 三渠道**（支付宝 / 微信 / 银行卡） | 一套支付适配��两处复用（下单 + 充值），零额外开发 |
| 单笔最小 | **100 分（1 元）** | 规避大量小额充值带来的手续费倒挂与风控噪音 |
| 单笔最大 | **500000 分（5000 元）** | 对齐常见预付卡/钱包限额，降低洗钱风险 |
| 单日累计上限 | **1000000 分（1 万元）**（可配） | 反洗钱与风控的常见做法；正常用户不受影响 |
| 充值赠送 | 一期做（P1），「充 100 送 10」式档位可配 | 提升充值转化；赠送记独立流水类型 `BALANCE_GIFT`，便于未来区分"可提现/不可提现"余额 |
| 充值单状态 | 待支付 → 成功 / 已关闭（超时 30 分钟，与订单关单一致） | 复用现有关单机制 |
| 充值不可使用优惠券 | ✅ 充值不属于商品交易，不参与优惠计算 | — |
| 充值是否可用余额支付 | ❌ 不允许（余额充余额无意义，且会绕过充值限额） | — |

#### 5.3.2 消费

| 规则项 | 规定 | 理由 |
| --- | --- | --- |
| **是否允许透支** | ❌ **绝对不允许**，`balance.allowOverdraft=false`，**不开放配置** | 透支本质是平台向用户放贷，涉及金融牌照与合规红线；且会带来坏账与催收问题 |
| **是否需要支付密码** | ✅ 余额支付必须校验支付密码（6 位数字，独立于登录密码，BCrypt 存储） | 余额是"已付款的钱"，盗用后果比盗刷银行卡更直接；独立密码可防止登录密码泄露牵连资金 |
| 密码错误策略 | 连续错 5 次锁定 30 分钟（可配） | 防撞库 |
| **小额免密** | 单笔 ≤ 3000 分（30 元）且当日累计 ≤ 10000 分（100 元）可跳过（可配，默认开），P1 | 高频小额场景（如小额加购）体验更顺；阈值可控，风险可承受 |
| **支付方式** | **单一**：余额 / 支付宝 / 微信 / 银行卡**四选一**，`pay_amount` 全额由选中的那一种支付 | 见 §2.3.8 恒等式；**不做组合支付**（v1.1 客户决策） |
| 余额支付金额 | `= pay_amount`（券后 + 运费后全额），**不支持只抵扣一部分** | — |
| 余额可用性 | `available ≥ pay_amount` 才可选；否则选项置灰 + 提示「余额不足，请先充值」 | 不做"余额不够就自动补渠道"的兜底 |
| 并发扣款 | CAS 乐观锁：`UPDATE user_balance SET available = available - ? WHERE user_id = ? AND available >= ?`，失败即提示"余额不足" | 防并发透支 |
| **待支付订单是否冻结余额** | ❌ **不冻结**（推荐） | 见下方专项说明 |

**为什么「待支付订单不冻结余额」**：
1. **无超卖风险**：余额只被该用户自己使用，不存在"被别人抢走"的竞争；而库存是全局共享资源，二者性质不同。
2. **避免复杂中间态**：冻结需要"下单扣、放弃解冻、超时解冻"三套逻辑，还要处理"用户看到余额被扣但订单未支付"的困惑与客诉。
3. **扣款是本地事务**：支付时扣余额不依赖外部渠道，速度极快，"付款时余额被别的操作占用"的窗口几乎为零。
4. **兜底**：并发提交两笔订单同时用余额时，CAS 保证第二笔失败并提示"余额不足"，不会出现透支。
> 余额账户仍保留 `frozen` 字段（一期恒为 0），为未来「保证金 / 预售定金 / 提现冻结」预留。

#### 5.3.3 单一支付方式（v1.1 客户决策：取消混合支付）

> **客户原话**：「去掉混合付款，单独支付就行，余额或者其他支付方式」。
> **结论**：一笔订单 = **一个支付方式** = **一个支付单**。要么全额用余额，要么全额走支付宝 / 微信 / 银行卡，**不做「余额 + 渠道」组合支付**。

**结构**：订单 → **1 个支付单**，记录 `channel`（`BALANCE` / `ALIPAY` / `WECHAT` / `BANKCARD` / `MOCK`）、金额（= `pay_amount`）、状态、渠道交易号。
**不再有父子支付单结构**（原「父支付单 + 多子支付单」设计作废），支付单模型可退回最简形态。

**① 结算：四种支付方式并列单选**

| 选项 | 展示 | 可用性判定 |
| --- | --- | --- |
| 余额支付 | 余额图标 + 「可用 ¥xxx.xx」 | `available ≥ pay_amount` 才可选；否则**置灰**并显示「余额不足，请先充值」+ 去充值入口 |
| 支付宝 | 「推荐」角标 + 费率/限额提示 | 渠道启用中 + 终端匹配 + 金额在限额内 |
| 微信支付 | 同上 | 同上 |
| 银行卡 | 同上 + 单笔限额提示 | 同上 |

- **互斥单选**，无「勾选余额抵扣」复选框、无抵扣额输入/滑块。
- 默认选中：**不默认选中任何项**（强制用户显式选择，避免"没看清就付了"的客诉）；余额充足时可将「余额支付」排在首位并预选（可配，见 Q-B17）。
- 选「余额支付」提交时校验支付密码（小额免密除外，见 §5.3.2）。

**为什么取消混合支付（对客户决策的确认性理由）**：
1. **退款复杂度归零**：不再有 PRO_RATA / BALANCE_FIRST / CHANNEL_FIRST 三种分配模式，也没有"尾差归入哪一段"的问题。
2. **对账更干净**：一笔订单的资金来源与去向都是单一的，渠道账单可逐笔一一对应。
3. **无跨来源回滚**：不会出现"余额扣了、渠道没付成"的双段回滚中间态。
4. **合规更稳**：不产生"部分资金沉淀为平台余额"的混合形态。
> 代价：余额不足时用户需先充值（多一步），但充值本身是已规划的能力，且充值有赠送活动（P1）可对冲体验损失。

**② 支付失败回滚（单一来源，无顺序问题）**

```
  提交订单（已选定支付方式）
       │
       ├─① 本地事务：券占用(LOCKED) + 库存校验
       │
       ├─② 分支 A：选「余额支付」
       │     ├─ CAS 扣减余额 → 写 BALANCE_CONSUME 流水
       │     ├─ 成功 ──► 订单置已支付，券置已使用，库存冻结转已售
       │     └─ 失败（余额不足/并发/下游异常）
       │           └─ 本地事务回滚：BALANCE_ROLLBACK（IN）+ 券解冻（瞬时、不可能失败）
       │
       └─② 分支 B：选「渠道支付」
             ├─ 外部调用：创建渠道支付单（不涉及余额）
             ├─ 成功 ──► 订单置已支付，券置已使用，库存冻结转已售
             └─ 失败 / 用户取消 / 超时
                   ├─ 关渠道单（closePayment，可能超时→重试+告警）
                   └─ 券解冻；渠道侧超时未支付自动关闭兜底
```

**要点**：两个分支**互不相交**，不存在"先退余额还是先关渠道单"的顺序问题（该问题随混合支付一并消失）。

**③ 退款去向（单一来源，唯一规则）**

| 订单支付方式 | 退款去向 | 实现 |
| --- | --- | --- |
| 余额支付 | **退回用户余额账户** | 写 `BALANCE_REFUND`（IN）流水 + 增加余额；**本地事务，无外部调用，即时到账** |
| 支付宝 / 微信 / 银行卡 | **原路退回原渠道** | 调用该渠道 `refund`；成功后写渠道退款流水 |
| 渠道原路失败/超期 | 审批后改退余额（`PAYC-08` P1） | super_admin 审批 + 审计日志 + 告知用户 |

> **余额订单不允许退到银行卡**：一期不做提现（见 Q-B4 / Q-B16），允许"余额 → 银行卡"的退款等于变相提现，会引入预付资金赎回的合规风险。
> 券的处理（整单退返还券、部分退不返还券）**按 §2.3.6 原规则执行，不受本次变更影响**。

**④ 部分退款（结论：一期做，P0）**

**最终结论**：**保留 P0，一期必须支持。**
**一句话理由**：优惠券上线后「一单多件只退其中一件」是高频售后场景，而分摊优惠已按行落库 —— 不支持部分退款就只能整单退（券返还 → 可被套利）或线下人工打款（账外资金、破坏对账恒等式）；且取消混合支付后已无跨来源拆分，部分退款只剩「按行算退款额 + 单一来源退回」，实现成本大幅下降。

**规则**：
1. 按订单行计算本次应退总额：`R = Σ(行金额 - 行促销优惠 - 行分摊优惠) + 应退运费`
2. **单一来源退回**：订单是余额支付 → `R` 全额退余额；订单是渠道支付 → `R` 全额原路退
3. **累计校验**：`Σ 历史退款 + 本次退款 ≤ 订单实付`，超出则拒绝
4. **尾差**：分行向下取整后求和，与 `R` 的差额（≤ 行数，单位「分」）归入最后一行，保证不丢不重
5. **运费**：部分退款默认不退运费；整单退款才退运费（可配）
6. **券**：部分退款不返还券（§2.3.6）

**示例**：订单应付 20000 分，用户选「支付宝」全额支付。退其中一行，行实付 8000 分。
→ `R = 8000`，**支付宝原路退 8000 分**（无拆分计算）。
→ 若该单是余额支付，则 `R = 8000` 全额退回用户余额。

**⑤ 余额冻结场景汇总**

| 场景 | 是否冻结 | 说明 |
| --- | --- | --- |
| 待支付订单 | ❌ 不冻结 | 支付时直接一次性扣减（见 §5.3.2） |
| 提现申请中 | ❌ 一期不做提现 | — |
| 争议/风控锁定 | ⚠️ 预留 | `frozen` 字段已留，一期恒为 0 |

#### 5.3.4 提现（待确认，一期不做）

客户未提及提现。**推荐一期不做**，理由：余额可赎回意味着它成为"预付资金账户"，通常涉及预付卡/支付业务相关的资质要求与备付金管理；且会引入提现审核、银行卡绑定、打款失败重试、手续费承担等一整套新流程。
**折中建议**：一期保持余额"单向"（充值 → 消费 → 退款退回），若用户强要求退出，可通过「人工客服 + 线下打款 + 后台调账」的方式个案处理（走 `MANUAL_ADJUST_OUT` 流水并留痕）。详见 Q-B4。

#### 5.3.5 余额明细与对账

**C 端余额明细（P0）**：类型 = 充值 `RECHARGE` / 消费 `CONSUME` / 退款退回 `REFUND` / 赠送 `GIFT` / 冲正 `REVERSAL` / 调账 `MANUAL`；每条含方向（IN/OUT）、金额、前后余额快照、关联单号、时间、说明文案。

**后台（P0）**：按用户查询余额与明细；super_admin 手工调账（必填原因 + 二次确认 + 独立流水类型 + 审计日志）。

**对账（三条恒等式，架构师必须保证表结构支持）**：

| # | 恒等式 | 说明 |
| --- | --- | --- |
| ① | `某用户余额 == 该用户 USER_BALANCE 账户流水净额` | 逐户校验，每日全量 |
| ② | `Σ 全体用户余额 == Σ 平台账户中 is_liability=true 的流水净额` | **余额总额 = 平台负债总额**，这是余额体系的总账校验 |
| ③ | `订单实付 == 该订单唯一支付单的金额`；`Σ 退款额 ≤ 订单实付`；**退款去向与订单 `pay_method` 严格一致** | 单笔校验，实时（单一支付方式后无需拆分校验） |

### 6.2 §6.5 资金流水：新增的流水类型

| 业务动作 | 类型码 | 方向 | 账户类型 | `is_liability` | 说明 |
| --- | --- | --- | --- | --- | --- |
| 用户充值 | `BALANCE_RECHARGE` | IN | `USER_BALANCE` | — | 用户余额增加 |
| 充值（平台侧收款） | `PLATFORM_RECHARGE_IN` | IN | `PLATFORM` | **true** | 钱进平台账户，但是**负债不是收入** |
| 充值赠送 | `BALANCE_GIFT` | IN | `USER_BALANCE` | — | 赠送余额；平台侧记为营销费用，不进收入 |
| 余额消费 | `BALANCE_CONSUME` | OUT | `USER_BALANCE` | — | 下单用余额支付 |
| 余额支付回滚 | `BALANCE_ROLLBACK` | IN | `USER_BALANCE` | — | 支付失败/关单回滚 |
| 退款退到余额 | `BALANCE_REFUND` | IN | `USER_BALANCE` | — | 退款的余额部分 |
| 余额提现 | `BALANCE_WITHDRAW` | OUT | `USER_BALANCE` | — | 一期不做（预留） |
| 余额手工调账 | `BALANCE_ADJUST_IN` / `BALANCE_ADJUST_OUT` | IN / OUT | `USER_BALANCE` | — | super_admin，必填原因 |
| 渠道手续费 | `CHANNEL_FEE` | OUT | `PLATFORM` | — | 按渠道费率（万分比）计算 |

> **核心设计要点（架构师必读）**：
> **用户余额账户是「负债账户」，不是收入账户。** 用户充值时钱确实进了平台银行账户，但它属于用户（用户可消费），不是平台的收入。因此：
> - `PLATFORM` 账户的每笔流水需带 `is_liability` 标记，区分「收入」与「代管的负债」；
> - **平台真实收入 = Σ PLATFORM 流水（排除 `is_liability=true`）**；
> - **平台负债总额 = Σ is_liability=true 的 PLATFORM 流水 = Σ USER_BALANCE 流水**；
> - 只有当余额被**消费**（`BALANCE_CONSUME`）时，对应的负债才结转为收入 —— 这一步需要一笔「负债结转」流水（建议类型 `LIABILITY_SETTLE`，方向：PLATFORM 账户 `is_liability` 由 true 转 false，金额等于消费额）。
>
> 这三条恒等式是余额体系对账的基石，表结构必须支持，否则后期无法证明「账实相符」。
