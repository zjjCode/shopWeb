## 1. 产品目标

本系统要交付一套**可独立运营、资金可溯源、第三方依赖可替换**的 B2C 电商商城：C 端买家完成「浏览 → 加购 → 下单 → 支付 → 收货 → 售后」的完整闭环，后台管理员完成「商品/库存/订单/用户/资金」的日常运营管理。

工程上要解决三个长期痛点：**重复代码**（公共能力统一封装）、**不可追溯**（每笔资金与每次状态变更都有流水与轨迹）、**第三方绑定死**（支付/物流/客服/短信走适配器，模拟实现与真实实现可一键切换）。

### 第一阶段成功标准（可验收）

| 维度 | 成功标准 |
| --- | --- |
| 交易闭环 | 一名新用户从注册到确认收货，全程可在系统内跑通，无需人工改库 |
| 资金可溯源 | 任意输入一个订单号，可还原该订单的全部分资金流水与状态变更轨迹，且「订单实付金额 = 该订单资金流水净额」校验通过 |
| 防超卖 | 100 并发抢购同一 SKU（库存 10），实际成单不超过 10 笔，库存不出现负数 |
| 幂等 | 下单/支付回调/退款接口重复提交同一幂等号，只产生一次业务结果，账不平为 0 |
| 后台可用 | 管理员可独立完成商品上架、库存调整、订单发货、退款审核、资金流水查询 |
| 第三方可切换 | 支付/物流/客服/短信四项在配置文件中一键切换 mock/真实，切换不改业务代码 |
| 工程规范 | 所有接口返回统一响应格式，异常统一处理，日志带 traceId，敏感信息脱敏 |

## 2. 角色定义

| 角色 | 代号 | 入口 | 核心能力 | 数据边界 |
| --- | --- | --- | --- | --- |
| 游客 | `guest` | 商城前台 | 浏览商品/分类/搜索、查看商品详情、浏览式加购（存本地） | 仅公开商品数据 |
| C 端买家 | `user` | 商城前台 | 注册/登录/登出；收货地址 CRUD 与默认地址；购物车管理；下单与支付（模拟）；查看自己的订单与物流；取消订单、申请退款；查看与自己相关的资金流水 | **仅能访问自己的数据**，越权访问返回 403 |
| 后台管理员 | `admin` | 管理后台 | 商品分类/商品/SKU/库存管理；订单管理（查看全部、发货、取消、退款审核）；用户查看与禁用；资金流水查询与对账；第三方适配器配置查看 | 可访问业务全量数据，**无权限**做手工调账以外的资金操作 |
| 超级管理员 | `super_admin` | 管理后台 | 在 `admin` 之上，额外拥有：管理员账号管理、角色与权限分配、手工调账、系统配置修改 | 全量（手工调账强制二次确认 + 留痕） |

## 3. 用户故事

### 3.1 用户与认证（AUTH）

1. 作为**游客**，我希望用手机号 + 密码注册账号，以便获得下单和追踪订单的能力。
2. 作为**买家**，我希望登录后获得 JWT 并在有效期内免登录，以便不用反复输入账号密码。
3. 作为**买家**，我希望在 Token 过期时自动续期，以便浏览/下单过程不会被突然踢出。
4. 作为**买家**，我希望登出后当前 Token 立即失效，以便在公共设备上保护我的账号。
5. 作为**管理员**，我希望后台有独立的登录入口与独立 Token 作用域，以便后台权限不会被 C 端 Token 冒用。
6. 作为**游客**，我希望不登录也能浏览和加购，以便降低首次使用门槛（登录后自动合并购物车）。

### 3.2 收货地址（ADDR）

1. 作为**买家**，我希望维护多个收货地址（省市区 + 详细地址 + 收货人 + 手机号），以便寄到家和公司不同地点。
2. 作为**买家**，我希望设置默认地址，以便下单时不必每次重复选择。
3. 作为**买家**，我希望在结算页直接新增/切换地址，以便下单流程不被打断。
4. 作为**买家**，我希望删除地址后历史订单仍保留当时的收货快照，以便日后对账和售后不丢信息。
5. 作为**系统**，我希望手机号与省市区在提交时做格式与级联校验，以便避免无效地址造成发货失败。

### 3.3 商品分类（CAT）

1. 作为**买家**，我希望按分类层级（最多三级）浏览商品，以便快速定位想买的品类。
2. 作为**管理员**，我希望在后台维护分类树、调整排序与启停，以便灵活组织前台展示结构。
3. 作为**管理员**，我希望分类下仍有商品时禁止删除，以便避免出现"孤儿商品"。
4. 作为**买家**，我希望商品页展示分类面包屑，以便知道自己在哪个品类下并能快速返回上级。

### 3.4 商品与 SKU（SKU）

1. 作为**管理员**，我希望维护商品（SPU）的名称、主图、图集、详情、分类、上下架状态，以便完整描述一个商品。
2. 作为**管理员**，我希望为商品定义多组规格（如颜色 × 版本）并自动生成 SKU 组合，以便不用逐个手工建 SKU。
3. 作为**管理员**，我希望为每个 SKU 单独设置编码、售价、成本价、重量与条码，以便精细化管理与成本核算。
4. 作为**买家**，我希望在详情页点选规格后实时看到对应的价格与库存，以便知道我选的款有没有货、多少钱。
5. 作为**买家**，我希望不可买的规格组合被置灰（零库存或未启用），以便我不会选到买不了的组合。
6. 作为**买家**，我希望商品列表支持按分类筛选与按价格/销量排序，以便快速找到目标商品。
7. 作为**管理员**，我希望商品先提交审核再上架，以便避免错误价格/文案直接对外可见。

### 3.5 库存（STK）

1. 作为**买家**，我希望下单成功后库存被锁定，以便我付款时不会被告知"刚好被人买走了"。
2. 作为**买家**，我希望取消订单或超时未付后库存被及时释放，以便商品能重新被其他人买到。
3. 作为**系统**，我希望库存扣减具备并发控制，以便高并发下单时不会出现超卖或负数库存。
4. 作为**管理员**，我希望看到可用/冻结/已售三类库存口径，以便清楚区分"能卖的"和"被订单占住的"。
5. 作为**管理员**，我希望手动入库/报损并填写原因，以便线下盘点结果能同步到系统。
6. 作为**管理员**，我希望每一次库存变动都留下流水（变动前后数量 + 关联单号 + 操作人），以便日后追查"这批货去哪了"。
7. 作为**管理员**，我希望库存低于预警阈值时在列表高亮，以便及时补货。

### 3.6 购物车（CART）

1. 作为**买家**，我希望把商品加入购物车并修改数量，以便一次性结算多件商品。
2. 作为**买家**，我希望勾选/取消勾选购物车条目，以便只结算其中一部分。
3. 作为**买家**，我希望失效商品（已下架/已删除/库存不足）被明显标记且不能结算，以便我不会因为一件失效商品卡住整个订单。
4. 作为**买家**，我希望看到加购后到结算前的价格变动提示，以便我对涨价有心理预期。
5. 作为**买家**，我希望登录后未登录期间的购物车被合并进来，以便不丢失已选商品。

### 3.7 订单（ORD）

1. 作为**买家**，我希望在结算页确认地址与金额明细（商品金额/运费/优惠/应付），以便付款前清楚自己付了什么钱。
2. 作为**买家**，我希望提交订单是幂等的，以便网络重试或误点两次不会生成两笔订单。
3. 作为**买家**，我希望取消未支付订单，以便改变主意后不用干等关单。
4. 作为**买家**，我希望已付款但未发货的订单可以申请退款并原路退回，以便快速拿回钱。
5. 作为**系统**，我希望超时未支付的订单自动关闭并释放库存，以便避免恶意占货导致商品卖不出去。
6. 作为**买家**，我希望查看订单详情中的状态时间轴，以便知道订单走到哪一步了。
7. 作为**管理员**，我希望为订单填写物流公司与运单号并发货，以便订单推进到已发货状态。
8. 作为**买家**，我希望收到货后确认收货，以及超时未确认时系统自动确认，以便订单能正常完成结算。
9. 作为**管理员**，我希望在后台按状态/时间/用户/订单号筛选订单，以便高效处理每日订单。
10. 作为**管理员**，我希望看到订单的每一次状态变更是谁、什么时候、因为什么改的，以便出现纠纷时能说清楚。

### 3.8 支付与资金（PAY / FUND）

1. 作为**买家**，我希望在模拟支付页确认付款，以便完整体验支付流程（真实渠道接入前）。
2. 作为**系统**，我希望支付回调是幂等的，以便渠道重复通知时不会重复入账。
3. 作为**财务/管理员**，我希望每一笔钱的进出都记成不可修改的流水（金额、方向、关联单号、时间、操作人），以便随时对账。
4. 作为**管理员**，我希望输入一个订单号就能看到该订单相关的全部资金流水，以便还原这笔钱的来龙去脉。
5. 作为**管理员**，我希望资金流水只能追加不能修改，记错了只能写反向冲正流水，以便账目具备审计性。
6. 作为**系统**，我希望资金记账与订单状态变更在同一事务内完成，以便不会出现"钱到了但订单还是未支付"。
7. 作为**管理员**，我希望按时间/类型/方向/操作人筛选流水并导出，以便做日结对账。

### 3.9 后台管理与公共能力（ADMIN / SEC）

1. 作为**管理员**，我希望有独立的后台登录页与会话管理，以便后台操作有独立的安全边界。
2. 作为**管理员**，我希望商品管理列表支持筛选、批量上下架与跳编辑，以便日常运营高效。
3. 作为**管理员**，我希望禁用异常用户账号，以便阻断恶意下单。
4. 作为**超级管理员**，我希望配置角色与接口权限，以便按岗位分配最小权限。
5. 作为**开发者**，我希望鉴权、参数校验、上传、分页、限流、响应封装都是中间件/工具模块，以便新接口不重复造轮子。
6. 作为**运维**，我希望所有日志带 traceId 且敏感字段脱敏，以便线上问题可快速定位且不泄露隐私。
7. 作为**运维**，我希望配置集中在配置中心并按环境隔离，以便一套代码部署多环境。

### 3.10 第三方适配（INTG）

1. 作为**开发者**，我希望支付/物流/客服/短信都抽象为统一适配器接口，以便替换服务商不改业务代码。
2. 作为**开发者**，我希望用配置开关在 mock 与真实实现间切换，以便开发阶段不依赖外部账号也能跑通。
3. 作为**管理员**，我希望在订单详情直接查看物流轨迹（mock 阶段返回模拟轨迹），以便给用户答复。
4. 作为**买家**，我希望注册/下单时收到短信通知（mock 阶段写日志），以便及时获知关键节点。
5. 作为**开发者**，我希望每个适配器都附带真实服务商的配置项清单与接入说明，以便后续接入时有据可依。
6. 作为**买家**，我希望在页面发起客服会话（mock 阶段为本地占位），以便有问题时能找到人。

### 4.1 用户与认证（AUTH）

| 编号 | 模块 | 需求描述 | 优先级 | 验收标准 |
| --- | --- | --- | --- | --- |
| AUTH-01 | 用户与认证 | 手机号/邮箱 + 密码注册，密码 BCrypt 加盐存储，注册后自动登录并返回 Token | P0 | 库中无明文密码；重复注册返回明确错误；注册成功直接返回 accessToken |
| AUTH-02 | 用户与认证 | 登录签发 JWT（Access Token 2h + Refresh Token 7d），支持刷新与登出（Token 黑名单/版本号失效） | P0 | Token 过期返回 401 且前端自动刷新；登出后旧 Token 请求返回 401 |
| AUTH-03 | 用户与认证 | JWT 鉴权中间件解析身份，RBAC 中间件按角色校验接口权限 | P0 | 无 Token → 401；角色不符 → 403；越权访问他人资源 → 403 |
| AUTH-04 | 用户与认证 | 未登录可浏览商品与加购（本地存储），登录后自动合并购物车 | P1 | 登录后购物车包含未登录期间条目，同 SKU 数量累加且不重复 |
| AUTH-05 | 用户与认证 | 刷新 Token 轮换 + 同账号多端互踢（可配） | P2 | 配置开启后，新登录使旧 Refresh Token 失效 |

### 4.2 收货地址（ADDR）

| 编号 | 模块 | 需求描述 | 优先级 | 验收标准 |

| PT-04 | 积分流水 | 与资金流水同构：流水号、幂等号、业务类型、关联单号、分值、方向、时间、操作人 | 二阶段 |
| PT-05 | 积分有效期 | 按发放批次设置有效期，到期自动失效（定时任务） | 二阶段 |

## 6. 关键业务规则

### 6.1 金额单位与精度

| 规则项 | 规定 |
| --- | --- |
| 存储单位 | **所有金额一律以「分」为单位的整数存储**（BIGINT/INT），数据库中不出现小数金额字段 |
| 展示 | 前端展示时 `元 = 分 / 100`，统一由工具函数格式化（保留 2 位小数、千分位） |
| 计算 | 全链路整数运算，**禁止使用浮点数做金额计算**；涉及除法（如分摊优惠）时，采用「按权重分摊 + 尾差计入最大项」算法，保证分项之和 = 总额 |
| 比例字段 | 折扣率/费率/税率一律用**万分比整数**存储（例：85 折 → `8500`；手续费率 0.6% → `60`），避免浮点 |
| 币种 | 第一阶段固定 `CNY`，但表结构保留币种字段以利扩展 |
| 精度校验 | 订单校验恒等式：`商品金额 - 优惠金额 + 运费 = 应付金额`，不满足则拒绝下单并告警 |

### 6.2 库存扣减时机（**推荐：下单锁定库存**）

**推荐方案：下单时预扣（冻结）库存，支付成功后转为实际扣减。**

| 环节 | 库存动作 | 说明 |
| --- | --- | --- |
| 提交订单 | `available -= n`，`frozen += n` | 预扣（冻结），不涉及已售 |
| 支付成功 | `frozen -= n`，`sold += n` | 确认扣减，商品正式出库 |
| 用户取消 / 超时关单 | `frozen -= n`，`available += n` | 释放冻结，回到可售 |
| 退款回仓 | `sold -= n`，`available += n` | 退货入库，回到可售 |

**推荐理由**：
1. **用户体验一致**：用户下单即知道"这个货我占住了"，不会在支付后被告知缺货 —— 这是「支付后扣减」方案最致命的体验问题。
2. **防超卖更彻底**：把库存竞争点前移到下单时刻，支付环节只是状态转移，并发窗口更短。
3. **可追溯**：冻结库存本身是"待履约"的可视化指标，运营一眼能看出有多少货被占住未付。
4. **兜底可控**：冻结有超时释放机制（30 分钟），恶意占货的影响被限制在半小时窗口内。

**并发控制实现要求**：
- 主手段：**条件更新（CAS）** —— `UPDATE sku_stock SET available = available - ?, frozen = frozen + ?, version = version + 1 WHERE sku_id = ? AND available >= ? AND version = ?`，以 `affectedRows` 判断是否成功，失败则重试或返回"库存不足"。
- 兜底：数据库层面加 `CHECK (available >= 0)` 约束（若数据库支持）或定时巡检任务。
- 可选增强：热点 SKU 加分布式锁（Redis）或内存锁（单机部署），但**不能以锁替代 CAS**。
- 库存变更必须写库存流水，且与订单/支付操作在同一事务内。

> 另提供配置开关 `stock.deductMode = 'order' | 'pay'`，默认值 `order`（下单锁）。如客户要求改为支付后扣减，改配置即可，但需在「待确认问题」中明确。

### 6.3 超时自动关单与库存回滚

| 规则项 | 规定 | 建议值 |
| --- | --- | --- |
| 关单时长 | 订单创建后待支付状态的存活时长，超时自动关闭 | **30 分钟**（配置项 `order.payTimeoutMinutes`） |
| 扫描策略 | 定时任务扫描超时候选订单，分页 + 状态条件更新（`WHERE status = 'PENDING_PAYMENT' AND created_at < ?`），避免全表扫描 | 每 **1 分钟**执行一次，单批最多处理 500 条 |
| 关单动作 | ① 订单状态 → `CANCELLED`，取消原因 = `TIMEOUT`；② 释放冻结库存；③ 写订单轨迹（操作人 = `SYSTEM`）；④ 调用支付适配器 `closePayment`；⑤ 若已产生预支付流水则写反向流水 | 五步在同一事务内完成（外部调用走事务提交后异步） |
| 幂等 | 关单以 `status` 条件更新保证只执行一次；重复扫描不会重复释放库存 | — |
| 自动确认收货 | 发货后 N 天未确认收货，自动置为已完成（释放可退款窗口，进入售后期） | **15 天**（配置项 `order.autoConfirmDays`） |
| 售后期 | 订单完成后可申请售后的时限 | 建议 **7 天**（见待确认问题 Q6） |
| 补偿机制 | 定时任务异常/服务重启时，启动时补偿扫描一次；提供后台"手动触发关单"按钮 | — |

### 6.4 取消与退款的边界

**订单状态机**

```
                    ┌──────────────────┐
                    │  已取消 CANCELLED │ ← 用户取消 / 管理员取消 / 超时关单
                    └──────────────────┘
                              ▲
   [提交订单]                 │              [支付成功]              [发货]           [确认收货/自动]
       │                      │                  │                    │                  │
  ┌─────────────┐  取消   ┌───┴─────────┐  退款   ┌──────────┐  退款  ┌──────────┐  售后  ┌──────────┐
  │ 待支付       │───────►│  待支付      │        │ 已支付    │───────►│ 已发货    │──────►│ 已完成    │
  │ PENDING_PAY │         │ (未产生资金)  │        │ PAID      │        │ SHIPPED   │       │ COMPLETED │
  └─────────────┘         └─────────────┘        └──────────┘        └──────────┘       └──────────┘
                                                       │                                      │
                                                       └──────────► 退款中 REFUNDING ◄─────────┘
                                                                          │
                                                                    ┌─────┴─────┐
                                                                    │ 已退款      │
                                                                    │ REFUNDED   │
                                                                    └───────────┘
```

**可取消 / 可退款矩阵**

| 订单状态 | 用户可取消 | 管理员可取消 | 可退款 | 退款方式 | 库存处理 |
| --- | --- | --- | --- | --- | --- |
| 待支付 `PENDING_PAYMENT` | ✅ 直接取消 | ✅ | ❌ **无需退款**（未产生资金流水） | — | 释放冻结库存 |
| 已支付（待发货）`PAID` | ✅ 取消即退款 | ✅ | ✅ 全额 | 原路退回，自动生成退款单 | 释放冻结库存 |
| 已发货（待收货）`SHIPPED` | ⚠️ 仅可申请退款，需管理员同意（建议需退货回仓） | ✅（拦截发货场景下可直接取消并全额退） | ✅ 全额或部分（协商） | 需退款审核；同意后原路退回 | 退款成功后 `sold → available` |
| 已完成 `COMPLETED` | ❌（售后期内可发起售后退款申请） | ⚠️ 仅售后期内，需填原因 | ✅ 部分或全额 | 需退款审核 | 仅退货退款场景回仓 |
| 已取消 `CANCELLED` | ❌ | ❌ | ❌ | — | — |
| 退款中 `REFUNDING` | ❌ | ❌ | ❌（已在流程中） | — | 冻结，待结果 |
| 已退款 `REFUNDED` | ❌ | ❌ | ❌ | — | 已回仓 |

**补充规则**
1. 待支付订单取消**不产生资金流水**（没有真实资金进出），但必须产生订单轨迹与库存流水。
2. 已支付订单的退款**必须产生一条 OUT 方向资金流水**，且退款金额 ≤ 该订单实付净额（已退金额累加校验，防重复退款）。
3. 部分退款允许（P1），需要订单行级别的退款明细，退款金额按行累加校验。
4. 退款必须由支付适配器执行（mock 阶段为模拟退款），**禁止直接改订单状态而不走退款流程**。
5. 退款失败（适配器返回失败）时，退款单置为"退款失败"并保留原因，支持人工重试，不自动改订单状态。

### 6.5 资金流水的记账方向定义

**方向枚举**：`IN` = 入账/收入（平台账户资金增加）；`OUT` = 出账/支出（平台账户资金减少）。

| 业务动作 | 业务类型码 | 方向 | 关联单号 | 说明 |
| --- | --- | --- | --- | --- |
| 用户支付订单 | `ORDER_PAY` | **IN** | 订单号 + 支付单号 | 买家付款入账（含商品金额 + 运费） |
| 订单全额退款 | `ORDER_REFUND` | **OUT** | 订单号 + 退款单号 | 退还买家，金额 = 实付 |
| 订单部分退款 | `ORDER_REFUND_PART` | **OUT** | 订单号 + 退款单号 | 退还买家部分金额 |
| 超时/用户取消（已支付） | `ORDER_CANCEL_REFUND` | **OUT** | 订单号 + 退款单号 | 与退款同向，独立类型便于统计取消率 |
| 支付渠道手续费 | `CHANNEL_FEE` | **OUT** | 支付单号 | mock 阶段记为 0 或按比例（可配） |
| 运费补收 | `FREIGHT_ADD` | **IN** | 订单号 | 改单补收运费（P1） |
| 运费退还 | `FREIGHT_REFUND` | **OUT** | 订单号 + 退款单号 | 随退款一并退还 |
| 手工调账 - 补记 | `MANUAL_ADJUST_IN` | **IN** | 手工单号 | super_admin 操作，必填原因 |
| 手工调账 - 冲减 | `MANUAL_ADJUST_OUT` | **OUT** | 手工单号 | super_admin 操作，必填原因 |
| 冲正流水 | `REVERSAL` | 与原流水**反向** | 原流水号 | 唯一允许的"改账"方式，必须关联原流水号 |

**记账铁律**
1. **单边不记账**：任何资金变动必须与订单/退款单状态变更在同一事务内完成，禁止先记账后改单。
2. **流水只增不改不删**：无 update/delete 接口；记错只能写 `REVERSAL` 反向冲正流水。
3. **余额快照**：每条流水记录 `before_balance` 与 `after_balance`，支持逐笔推演账户余额。
4. **对账恒等式**：`某订单实付金额 = 该订单所有 IN 流水之和 - 所有 OUT 流水之和`（不含手续费时）；含手续费时 `实付 = IN 之和 - 退款类 OUT 之和`。
5. **操作人必填**：`operator_type`（USER / ADMIN / SYSTEM）+ `operator_id`，定时任务写入 `SYSTEM`。
6. **金额为正**：流水金额一律存正数，方向由 `direction` 字段表达，不使用负号。

### 6.6 幂等号的生成与作用域

| 规则项 | 规定 |
| --- | --- |
| 传递方式 | 客户端在写操作请求头携带 `Idempotency-Key: <UUID v4>`（下单、支付、退款、库存调整必传；其它写操作可选） |
| 服务端兜底 | 未传 Key 时，服务端按 `业务类型 + 业务单号 + 操作序号` 生成确定性 Key（如支付回调固定用 `PAY_CALLBACK:{outTradeNo}`） |
| 作用域 | `scope = 业务类型 + 用户ID（或订单号/支付单号）`；唯一索引为 `(scope, idempotency_key)`，**不做全局唯一**，避免跨用户/跨业务冲突 |
| 存储 | 独立幂等表：`scope`、`idempotency_key`、`request_fingerprint`（请求体 hash）、`response_snapshot`（首次响应 JSON）、`status`（PROCESSING/SUCCESS/FAILED）、`expire_at` |
| 命中语义 | ① `SUCCESS` 且 fingerprint 一致 → **直接返回首次响应快照**，不重复执行业务；② fingerprint 不一致 → 返回 **409**，提示"幂等号复用但参数不同"；③ `PROCESSING` → 返回 **409 + 稍后重试**；④ `FAILED` → 允许重新执行 |
| 有效期 | 订单创建类 **24 小时**；支付/退款类 **7 天**（与渠道对账周期对齐）；到期由定时任务清理 |
| 并发控制 | 插入幂等记录时用唯一索引抢占，抢占失败的并发请求走"命中语义"分支，天然防并发重复提交 |
| 支付回调 | 除幂等表外，额外以 `out_trade_no` + `trade_status` 做业务层状态机幂等（状态已终态则直接返回成功），**双重保险** |

### 6.7 第三方适配器统一约定

| 适配器 | 统一接口方法 | mock 实现 | 真实接入配置项 |
| --- | --- | --- | --- |
| 支付 `PaymentAdapter` | `createPayment` / `queryPayment` / `refund` / `closePayment` / `verifyCallback` | 生成模拟支付单 + 模拟支付页 + 模拟异步回调 | `appId`、`mchId`、`apiKey`、`privateKey`、`publicKey`、`gatewayUrl`、`notifyUrl`、`signType`、`sandbox` |
| 物流 `LogisticsAdapter` | `queryTrace` / `subscribe`（可选） | 返回按时间生成的模拟轨迹（已揽收→运输中→派送中→已签收） | `provider`、`apiKey`、`queryUrl`、`subscribeUrl` |
| 客服 `SupportAdapter` | `createSession` / `sendMessage` / `getMessages` / `closeSession` | 本地内存会话，消息存储到本地表 | `provider`、`appKey`、`appSecret`、`apiUrl`、`webUrl` |
| 短信 `SmsAdapter` | `sendVerifyCode` / `sendNotify` / `checkCode` | 验证码写日志/控制台 + 本地校验（配置可返回固定验证码便于测试） | `provider`、`accessKeyId`、`accessKeySecret`、`signName`、`templateCode`、`region` |

**统一约定**
1. 所有适配器通过工厂 `AdapterFactory.get(type)` 获取，实现选择由配置 `adapter.<type>.provider = 'mock' | 'alipay' | 'wechat' | ...` 决定。
2. 所有适配器方法返回统一结构 `{ success, code, message, data, raw }`，失败不抛裸异常，由调用方决定是否降级。
3. 统一超时（默认 5s）、重试（默认 2 次，仅幂等接口）、熔断降级；第三方失败**不得阻塞主流程**（如物流查询失败只影响轨迹展示）。
4. 所有外部调用落第三方调用记录表（P1），请求/响应脱敏存储。
5. 每个适配器附一份 `docs/adapters/<name>.md` 接入说明（申请流程 + 配置项 + 回调验签 + 联调步骤）。

## 8. 待确认问题（需客户拍板）

> 每道题均给出**推荐答案与理由**，客户可直接回复「全部按推荐」或针对某题给出不同选择。

| # | 问题 | 选项 | 推荐 | 推荐理由 |
| --- | --- | --- | --- | --- |
| **Q1** | 数据库选型？ | A. MySQL 8.0 / B. PostgreSQL 15 / C. 由架构师定 | **A. MySQL 8.0** | 生态与运维资料最丰富，Express 侧 ORM（Prisma/Sequelize）支持成熟，金额用 BIGINT、事务与行锁行为稳定；若后续需要 JSONB/更强约束再评估 PG |
| **Q2** | 库存扣减时机？（见 6.2） | A. 下单锁定库存 / B. 支付成功后扣减 | **A. 下单锁定库存** | 避免"付完款才发现没货"的致命体验问题；并发窗口更短，配合 30 分钟超时释放可限制恶意占货影响。已提供配置开关，改 B 只需改配置 |
| **Q3** | 待支付订单超时时长？ | A. 15 分钟 / B. 30 分钟 / C. 60 分钟 | **B. 30 分钟** | 兼顾"用户凑单/切换支付方式"的真实耗时与库存周转效率；电商行业常见值，且可后台配置随时调整 |
| **Q4** | 是否包含运费？运费规则？ | A. 不含运费（全场包邮）/ B. 满额包邮 + 未满固定运费 / C. 按地区/重量计费 | **B. 满 ¥99 包邮，未满收 ¥12** | 逻辑最简单、可配置、便于验证金额链路又不过度复杂；C 的重量/地区计费需要运费模板，建议放 P1 或二阶段 |
| **Q5** | 退款是否需要审批流？ | A. 已付款未发货自动退，已发货/已完成需人工审核 / B. 全部自动退款 / C. 全部人工审核 | **A** | 未发货场景自动退可大幅减少客服工作量且风险低（货未出仓）；已发货涉及退货回仓与资金损失，需要人工把关。第一阶段的"已发货退款"放 P1 |
| **Q6** | 售后期时长与规则？ | A. 7 天无理由 / B. 15 天 / C. 不支持售后 | **A. 7 天无理由**（售后退款接口 P1） | 符合国内电商惯例与用户预期；第一阶段先支持"已付款未发货"的取消退款，售后退款流程放 P1，不影响一期交付 |
| **Q7** | 是否需要多规格图片（每个规格值绑定图片）？ | A. 不需要，仅用主图+图集 / B. 需要 | **A. 一期不需要**（已列 P2） | 会显著增加商品编辑与 SKU 数据模型复杂度；一期用"主图 + 图集"已能满足展示，后期可按 P2 平滑扩展 |
| **Q8** | 商品是否需要上下架审核流？ | A. 不需要，管理员直接上下架 / B. 需要提交 + 审核 | **A. 一期不需要**（已列 P1） | 一期管理员规模小，审核流增加操作步骤与状态复杂度；若后续有多运营账号再启用 P1 |

## 9. 附：术语表

| 术语 | 含义 |
| --- | --- |
| SPU | 商品聚合单元（一个商品），如「XXX 智能手机」 |
| SKU | 最小库存单位（具体规格组合），如「XXX 智能手机 陨石黑 8G+128G」 |
| 可用库存 | 当前可售数量（`available`） |
| 冻结库存 | 已被待支付订单占用但未出库的数量（`frozen`） |
| 已售库存 | 已支付并出库的数量（`sold`） |
| 幂等号 | 保证同一写操作重复提交只执行一次的唯一标识（`Idempotency-Key`） |
| 资金流水 | 每一笔资金进出的不可变记录 |
| 订单轨迹 | 订单状态每一次变更的记录（谁、何时、从什么状态到什么状态、为什么） |
| 适配器 | 将第三方服务（支付/物流/客服/短信）封装为统一接口的中间层 |
| 冲正流水 | 用于更正错误流水的反向流水（唯一允许的"改账"方式） |
