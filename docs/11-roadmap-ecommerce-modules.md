## 二、分阶段排期

### 阶段 12 · 资金域闭环（P0，必先完成才能上线）
**目标**：把「下单 → 支付 → 退款 → 对账」资金链路从代码层补全到可运营。
| 模块 | 核心功能 | 关键产出 | 依赖 | 工作量 |
| --- | --- | --- | --- | --- |
| T070 余额/充值 API | 余额开户/明细、充值建单（委托 `buildConfiguredPayUrl`）、余额支付/退款（复用 `FundService.recordBalancePayment/Refund`） | `BalanceService`/`RechargeService` API + 控制器/路由 | 缺口 #2/#3 接缝（已完成）、`FundService` | 2 批次 |
| T080 退款审核/重试 | 退款申请/审核流转、CHANNEL 退款经 `RefundAdapter`、重试 Worker（`retryRefund.job.ts`）接 `markChannelFailed` 指数退避 | `RefundService` 补全 + `jobs/handlers/retryRefund.job.ts` | 缺口 #3 接缝、T091 调度 | 2 批次 |
| T090 对账 | 用户余额账户 + 平台账户双视图对账，恒等式 L1/L2/L3 校验 | `ReconciliationService` + 后台对账页 API | `FundService` 流水 | 1.5 批次 |
| T091 后台支付/任务 | 支付方式管理台、`closeTimeoutOrder`/`autoConfirm`/`retryRefund` 调度落地 + 分布式锁选主 | `jobs/*` 补全、`AdminPaymentMethodController` | 配置 `adapter.payment.provider` | 1.5 批次 |

## 三、依赖与风险

1. **环境阻塞（最高优先）**：当前**无 MySQL / Redis 实例**，T070/T080/T090/T110 等资金与集成测试均无法真实验证。需在阶段 12 前准备实例并跑 `prisma migrate dev` + `prisma/sql/001_add_check_constraints.sql` + `npx prisma db seed`。
2. **渠道密钥**：缺口 #2/#3 的 `RealPaymentAdapter`/`RealRefundAdapter` 骨架已就位，但真实签名/回调需 `alipay`/`wechat` 密钥就绪后才能接；生产 `provider==='mock'` 已被 `assertProductionSafety` 拒启动（70010）。
3. **复用既有原语**：余额/退款记账务必复用 `FundService.recordBalance*`，不得内联三流水（T061 决策）；退款路由复用 `RefundService.resolveRefundTarget` + `RefundAdapter` 接缝。
4. **前端滞后**：T100/T101 前端页面完全未启动，阶段 12~15 的后端模块需同步排期前端，避免「后端通、前端空」。

## 四、建议落地顺序（一句话）
**先打通资金闭环（阶段 12）→ 再做增长与会员（阶段 13）→ 然后商品体验（阶段 14）→ 履约客服（阶段 15）→ 运营风控（阶段 16）→ 全程穿插验证与文档（阶段 17）**。阶段 12 是上线硬前置，应优先投入。
